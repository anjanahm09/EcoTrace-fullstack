# EcoTrace — Carbon Footprint Calculator 🌱

EcoTrace is a Java Full Stack web application designed to calculate, record, and monitor carbon emissions generated by organizational activities. It enables users to record emission-related activities, select compatible emission factors, calculate emissions, and view results through a dashboard.

The application uses **Java Spring Boot** for the backend, **React with Vite** for the frontend, and **MySQL** for data persistence. It also provides REST APIs, Swagger documentation, and role-based access control for Admin, Stakeholder, and Auditor users.

## Project Overview

Organizations generate greenhouse gas emissions through fuel consumption, electricity usage, purchased materials, transportation, waste management, and other business activities.

EcoTrace provides a centralized application for recording these activities and calculating associated emissions using emission factors with documented units and source information.

The application supports activities across Scope 1, Scope 2, and Scope 3, subject to the categories and factors configured in the system.

### Project Objectives

- Calculate emissions from activity data and compatible emission factors.
- Organize emission records by greenhouse-gas accounting scope.
- Maintain emission-factor source and methodology information.
- Display recorded activities and emission summaries through a dashboard.
- Restrict access to organizational data based on user roles.
- Provide API documentation and a foundation for supply-chain emissions tracking.

## Features

### 1. Carbon Activity Management

- Record activities with an activity name, organization, scope, category, quantity, unit, and date.
- Associate activities with emission factors.
- Save calculated emissions and review activity records.
- View emissions summaries through the dashboard.

### 2. Scope-Based Emissions

**Scope 1 — Direct emissions**

Records direct emissions from sources owned or controlled by an organization, such as fuel combustion.

**Scope 2 — Purchased energy**

Records emissions associated with purchased electricity and other applicable purchased energy categories, according to the configured factors.

**Scope 3 — Value-chain emissions**

Records applicable indirect value-chain activities, including purchased goods and services and upstream transportation and distribution, where the corresponding categories and factors are available.

> The presence of a scope in the application does not by itself mean that every category or accounting method for that scope has been implemented.

### 3. Emission Factor Management

Emission factors can include:

- Factor name and category
- Activity unit
- Emission factor value
- Source name and source URL
- Dataset version and reference year
- Geography
- Boundary description
- Access date
- Illustrative/demo status

Factors must be compatible with the activity unit. Illustrative factors are not suitable for official calculations.

### 4. Freight Emissions

For compatible freight factors, the application supports a tonne-kilometre calculation based on freight mass and distance.

- Freight mass is recorded in tonnes.
- Transport distance is recorded in kilometres.
- Freight activity is calculated in tonne-kilometres.
- Emissions are calculated using a compatible freight emission factor.

The application includes duplicate transport-leg prevention behavior that should be verified against the current implementation and deployment.

### 5. Dashboard and Reporting

- View saved carbon activities.
- Review total emissions from recorded activities.
- View emissions grouped by scope.
- Review changes to totals after new activities are recorded.

### 6. Role-Based Access Control

The application uses Spring Security to restrict access based on user roles.

- **Admin:** Administrative operations, including emission-factor creation.
- **Stakeholder:** Permitted access to the stakeholder's organization and activities.
- **Auditor:** Read-only access to permitted information.

## System Architecture

EcoTrace follows a frontend-backend-database architecture.

1. **Frontend:** React provides the user interface for recording activities and reviewing emissions.
2. **Backend:** Spring Boot exposes REST endpoints, applies validation and authorization, and performs emissions calculations.
3. **Database:** MySQL stores application data, including organizations, user accounts, activities, and emission factors.
4. **API documentation:** Swagger UI documents available endpoints and allows authorized API testing.

```text
User
  |
  v
React + Vite Frontend
  |
  | REST API / HTTP
  v
Spring Boot Backend
  |
  +-- Spring Security
  |
  +-- Activity and Emission Calculations
  |
  +-- Emission Factor Management
  |
  v
MySQL Database
```

## Emission Calculation

### General calculation

For an activity with a compatible emission factor:

**Emissions (kg CO₂e) = Activity quantity × Emission factor**

The activity quantity and factor must use compatible units.

### Freight calculation

**Freight activity (tonne-km) = Mass (tonnes) × Distance (km)**

**Freight emissions (kg CO₂e) = Freight activity (tonne-km) × Freight emission factor**

Example:

- Freight mass: 2 tonnes
- Distance: 100 km
- Freight activity: 2 × 100 = 200 tonne-km
- Example factor: 0.2222 kg CO₂e/tonne-km
- Calculated emissions: 200 × 0.2222 = 44.44 kg CO₂e

The factor above is an example used in project testing, not a universal freight factor. Its source, license, geography, vehicle assumptions, and emissions boundary must be checked before reporting results.

## Installation and Setup

### 1. Clone the repository

After publishing the project to GitHub:

```bash
git clone YOUR_GITHUB_REPOSITORY_URL
cd EcoTrace-fullstack
```

Replace `YOUR_GITHUB_REPOSITORY_URL` with your actual repository URL.

### 2. Configure MySQL

Create the database:

```sql
CREATE DATABASE ecotrace_db;
```

Configure the database username and password using environment variables or your IDE's run configuration.

Example environment variables:

```text
DB_URL=jdbc:mysql://localhost:3306/ecotrace_db?createDatabaseIfNotExist=true
DB_USERNAME=your_mysql_username
DB_PASSWORD=your_mysql_password
```

Do not place real credentials in source code or commit them to GitHub.

### 3. Configure the backend

The backend should use environment-driven database configuration. For example:

```properties
spring.application.name=ecotrace
server.port=${PORT:8080}

spring.datasource.url=${DB_URL:jdbc:mysql://localhost:3306/ecotrace_db?createDatabaseIfNotExist=true}
spring.datasource.username=${DB_USERNAME:root}
spring.datasource.password=${DB_PASSWORD}

spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=false
spring.jpa.open-in-view=false

spring.jackson.serialization.write-dates-as-timestamps=false
springdoc.swagger-ui.path=/swagger-ui.html
```

Keep the properties consistent with the current backend configuration.

### 4. Configure the frontend

Create a local `.env` file inside the frontend directory:

```dotenv
VITE_API_BASE_URL=http://localhost:8080/api
```

This URL is for local development. The production deployment must use the deployed backend URL.

## API Documentation

EcoTrace provides REST endpoints for accessing application data and performing permitted operations.

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/health` | Health check |
| GET | `/api/categories` | Retrieve activity categories |
| GET | `/api/factors` | Retrieve emission factors |
| GET | `/api/organizations` | Retrieve organizations, subject to authorization |
| GET | `/api/activities` | Retrieve permitted activities |
| POST | `/api/activities` | Create an activity, subject to authorization and validation |
| GET | `/api/reports/summary` | Retrieve an emissions summary |
| GET | `/api/factor-admin` | Retrieve emission factors |
| GET | `/api/factor-admin/{id}` | Retrieve an emission factor by ID |
| POST | `/api/factor-admin` | Create an emission factor; Admin only |

Consult Swagger UI for the exact request fields, response formats, and security requirements.

## User Roles and Permissions

| Operation | Admin | Stakeholder | Auditor |
|---|---|---|---|
| Read permitted emission factors | Yes | Yes | Yes |
| Create emission factors | Yes | No | No |
| Read organizations | Yes | Restricted | Restricted |
| Read permitted activities | Yes | Own organization / assigned stage, where configured | Permitted read access |
| Create activities | Yes | Permitted organization, subject to validation | No |

Actual permissions are determined by the current backend security configuration. Test authorization behavior before presenting the table as a complete access-control specification.

## Deployment

The frontend and backend can be deployed separately.

### Backend deployment

1. Publish the backend source to GitHub.
2. Create a Java 21 web service on a hosting provider that supports Spring Boot.
3. Create a managed MySQL database.
4. Configure the database connection through environment variables.
5. Configure a secure port and the production CORS allowlist.
6. Deploy the service.
7. Test the deployed health endpoint, Swagger UI, and protected endpoints.

### Frontend deployment

1. Publish the frontend source to GitHub.
2. Create a frontend deployment on a static hosting provider.
3. Set the build command to:

```bash
npm run build
```

4. Set the output directory to:

```text
dist
```

5. Configure `VITE_API_BASE_URL` to the deployed backend base URL ending in `/api`.
6. Redeploy the frontend and test API calls from the live website.

### Production checklist

- Use HTTPS.
- Configure CORS for the real frontend domain.
- Keep passwords and secrets in the hosting provider's secret settings.
- Use a managed database with backups and suitable access controls.
- Verify user roles and cross-organization authorization.
- Avoid development-only database schema settings for production.
- Test the complete deployed application.

## Security Considerations

- User passwords should be stored using a secure password-hashing mechanism.
- Protected endpoints should require authentication and authorization.
- Stakeholders must not access other organizations' data.
- Auditors should not be allowed to modify records.
- Production credentials must not be committed to source control.
- Emission-factor creation should be restricted to authorized administrators.
- Validate user input and reject incompatible units or invalid quantities.

## Limitations

- Calculation accuracy depends on the activity data and selected emission factor.
- A sourced factor is not automatically suitable for every geography, vehicle type, reporting year, or emissions boundary.
- Illustrative factors are for demonstration and must not be presented as verified official results.
- Support for all Scope 3 categories, all supply-chain stages, and both Scope 2 accounting methods must be verified against the implementation.
- This application is a project-level carbon accounting tool and is not, by itself, an independently verified corporate greenhouse-gas inventory.
